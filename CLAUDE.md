# Trelby

Screenplay writing app. Python 3 + wxPython (GUI), lxml, reportlab (PDF export). Package code is in `trelby/`, tests in `tests/`, DocBook manual sources in `doc/`.

## Package layout

- `trelby/` itself: the entry point (`trelby.py`) and the wx-free core: `config`, `commands`, `keys`, `formats`, `misc`, `util`, `textutil`, `translations`, `undo`, `textfmt`, `spellcheck`, `thesaurus`, `speech`.
- `screenplay/`: the script model (see [below](#the-screenplay-model)), with `screenplay/export/`, and the parts of a script it holds (`line`, `titles`, `headers`, `characterprofiles`, `locations`, `worldbuilding`, `beatboard`, `pagelock`, `autocompletion`, `autocompletiontype`). `importers/`: one module per import format.
- `ui/`: the main window, the editor widget and the GUI helpers (`trelbyframe`, `trelbyctrl`, `menus`, `scriptactions`, `scriptpainter`, `toolbar`, `statusbar`, `gutil`, `widgets`, `theming`, `icons`, `fileio`, `configgui`, `globaldata`, `myimport`...).
- `dialogs/`: the dialogs (`*dlg.py`, plus the title and header page previews), and `dialogs/configpages/`, the Settings dialog's pages.
- `reports/`: the reports and the dialogue chart (wx-free), their windows (`reportwindow`, `reportframes`).
- `pdf/`: page layout and PDF output: `pml`, `writer` (the PDF generator, imported as `pdf`), `fontinfo`, `truetype`, `mypager`.
- `mcpserver/`: the MCP server (`server`, `tools`, `app`; see [MCP server](#mcp-server)).

File names stay the same when a module moves into a folder, and code imports it under its old name: `import trelby.ui.gutil as gutil`, `import trelby.reports.scenereport as scenereport`. The exceptions are `mcpserver/` (`import trelby.mcpserver.tools as mcptools`), `pdf/writer.py` (`as pdf`) and `reports/reportframes.py`. Apart from `screenplay/` (importing any of its modules loads the whole model, which is wx-free), the folders' `__init__.py` files are empty, so importing a module from a folder doesn't import wx unless that module does.

## Dev setup (Windows)

```bash
py -3 -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
```

`make` and `xsltproc` are not needed for day-to-day work.

## Run / test

```bash
.venv/Scripts/python trelby.py --test trelby/sample.trelby   # --test: config goes in ./.trelby/
.venv/Scripts/python -m pytest
```

Without `--test`, config is written to `%USERPROFILE%\Trelby\conf` (Windows) or `~/.config/trelby` (Unix).

## Generated files: do not commit

- `trelby/names.txt.gz`, `trelby/dict_en.dat.gz`, `trelby/thesaurus_en.dat.gz`: gzipped copies of `names.txt` / `dict_en.dat` / `thesaurus_en.dat`, produced by `make` (or `gzip -c`). `fileio.loadMaybeCompressedFile` prefers the uncompressed file, so running from source doesn't need them; they exist only for packaging (PyPI `package_data`, Debian, the exe).
- `trelby/manual.html`, `trelby/trelby.1.gz`: built from `doc/` by `make`, which needs `xsltproc` plus DocBook XSL stylesheets at Linux paths (use WSL). Without them, Help → Manual is the only thing that breaks.
- `.venv/`, `build/`, `dist/`, `*.spec`, `.trelby/`.

## Building a Windows exe (PyInstaller)

```bash
sh tools/build-exe.sh
```

It installs PyInstaller if needed, regenerates the `.gz` files, and builds `dist/Trelby/` (`Trelby.exe` + `_internal/`, which must stay together). Takes about 30s. It refuses to run while `Trelby.exe` is open, since that locks `dist/Trelby/`. If you add a new data file, add an `--add-data` for it in the script.

The same script builds on macOS (`dist/Trelby.app`) and Linux (`dist/Trelby/Trelby`), leaving out the Windows-only parts (pyttsx3 / SAPI, `WebView2Loader.dll`); `PY` overrides the python it uses (default `.venv/Scripts/python` or `.venv/bin/python`). `.github/workflows/build.yml` runs the tests and the script on all three on every push to main and every PR, uploading a zip / tar.gz of each as an artifact; pushing a `v*` tag also makes a draft GitHub release with them. The builds aren't signed, so macOS Gatekeeper and Windows SmartScreen warn about them.

When the user asks for a "build", "Windows build" or "exe" to test changes, run the full test suite, then the script, then confirm the result. Check that `build/Trelby/PYZ-00.toc` lists any new `trelby.*` modules, and that the exe starts: launch it, then check that `tasklist //V //FI "IMAGENAME eq Trelby.exe" //FO LIST` shows a `Trelby - ...` window title rather than an error dialog. Leave it running for them, and give the path to `dist/Trelby/Trelby.exe`.

## MCP server

AI assistants can read and edit scripts over MCP, with one set of tools (`makeServer` in `trelby/mcpserver/server.py`) served three ways:

- **Files on disk:** `.venv/Scripts/python -m trelby.mcpserver` (stdio). Every write saves the file with a `.bak` backup, and doesn't reach a copy of the script open in the app.
- **In the app:** Settings → MCP Server turns on an HTTP server at `http://127.0.0.1:7789/mcp` (`trelby/mcpserver/app.py`, off by default, `mcpEnabled` / `mcpPort` in the global config). It edits the open scripts live: the `path` argument picks a script, defaulting to the active tab. Calls run in the GUI thread via `wx.CallAfter`; edits are undoable and refused while a modal dialog is open.
- **Bridge:** `python -m trelby.mcpserver --app [--port N]` is a stdio server that forwards to the app, for Claude Desktop, which can only start servers. The exe runs it as `Trelby.exe --mcp-bridge [--port N]` (checked in `trelby.trelby.main` before any wx startup; stdio works even though the exe is windowed). The settings page has a button that copies its config entry, in whichever form is running.

The operations are in `trelby/mcpserver/tools.py` (`mcptools`), which needs neither the MCP SDK nor wx (see [Model and GUI modules](#model-and-gui-modules)): `FileDoc` (file on disk) and `LiveDoc` (an `Editor` on a script in memory, with undo; `mcpapp.AppDoc` (`mcpserver/app.py`) uses the tab's `ctrl.ed` and adds the GUI refresh). Edits get an `Editor` (`FileDoc` makes a throwaway one). Every write needs the revision (a content hash) from an earlier read. Tests: `tests/test_mcptools.py`, `tests/test_mcpserver.py`.

The `mcp` SDK is an optional extra (`pip install trelby[mcp]`, entry point `trelby-mcp`); without it the app runs normally and the settings page says the server isn't available. The exe always bundles it (about 25 MB of the ~125 MB `dist/Trelby/`): `tools/build-exe.sh` installs it if missing and fails if the lazily imported MCP/uvicorn modules are missing from `PYZ-00.toc`. To test the exe's server without touching your real settings, run it with `--test` from the repo root and add `MCP/Enabled:True` (and `MCP/Port:N` if a source Trelby already holds 7789) to `.trelby/default.conf`.

For a stdio client config, use the venv's python as the command, `["-m", "trelby.mcpserver"]` (plus `"--app"` for the bridge) as args, and `PYTHONPATH` set to the repo root in `env` (Claude Desktop has no `cwd` option, and trelby isn't pip-installed in the venv). For the exe it's just `Trelby.exe` with `["--mcp-bridge", "--port", "N"]`. Claude Desktop rewrites its config file while running, so quit it fully (tray → Quit) before editing `claude_desktop_config.json`.

## The screenplay model

`trelby/screenplay/` is the script model, with a map of its modules in `__init__.py`. It has two classes, both built from per-area mixins that call each other through `self`:

- `Screenplay` (`model.py`, usually `sp`) is the document: lines, title pages, headers, config, character profiles, world building, and the page breaks worked out from them. Its methods read the script or change lines at positions they're given (`structure`, `wrapping`, `pagination`, `locks`...).
- `Editor` (`editor.py`, usually `ed`) is an editing session on one: `ed.sp`, the cursor (`ed.line` / `ed.column`), the selection (`ed.mark`), the scroll position, the auto-completion list, the typing style and the undo history (`ed.undoHistory`). It has the commands (`ed.cmd("moveLeft")`, `commands`, `textinput`) and every undoable edit (`editing`, `selection`, `formatting`, and the `*EditMixin` classes in `centering`, `dualdialogue`, `locks`, `sceneoutline`). Undo objects (`trelby/undo.py`) take the Editor, since they restore the cursor too.

`MyCtrl` has both (`self.sp`, `self.ed`) and makes a new Editor whenever it gets a new script. Code that only works on a script from the outside is plain functions of `sp`: `export/` (`export.generateFDX(sp)` etc.), `render` (pml page layout for PDF and the page views), `compare`, `proofing`, and `fileformat` (behind `sp.save()` / `Screenplay.load()`).

- The rule for where a method goes: if it records undo, or reads or moves the cursor or selection, it's an Editor method; otherwise it's a Screenplay method. New read-only consumers (exports, reports) go in plain functions, not on either class.
- The wrapping functions (`rewrapPara`, `rewrapElem(s)`, `reformatRange`, `reformatAll`...) take an optional `cursor` (anything with `line` / `column`) that they keep on the same text. The Editor has same-named wrappers that pass itself, and default to the cursor's paragraph / element. `ed.reformatAll()` insists on an empty undo history; `sp.reformatAll()` doesn't check.
- The cursor position saved in a file is `sp.cfg.cursorLine` / `cursorColumn`: `load` sets them, a new `Editor(sp)` starts there, and `ed.save()` stores the cursor before saving. `sp.save()` writes whatever they hold, so save through the Editor when there is one.
- Tests that edit use `u.newEditor()` / `u.loadEditor()` / `u.loadStringEditor()` (`tests/u.py`) and reach the document as `ed.sp`; `ed._validate()` checks the cursor and then the script.
- `import trelby.screenplay as screenplay` still gives `Screenplay`, the `LB_*` / element type constants and the `datatypes` classes. The package's `__init__` must import `constants` before anything else, because `config` and `line` import the package while it's still loading.
- The parts of a script that a `Screenplay` holds live in the package too, imported under their old names (`import trelby.screenplay.titles as titles`, `from trelby.screenplay.line import Line`): `line`, `titles`, `headers`, `characterprofiles`, `locations`, `worldbuilding`, `pagelock`, `autocompletion` / `autocompletiontype`. Since importing any of them runs the package's `__init__` first, each can be the first trelby import (`line` and `undo` couldn't before, when `line` was outside the package).
- Find and replace: `screenplay/search.py` has `FindOptions` (text, `matchCase`, `wholeWord`, `up`, `elementTypes`: a frozenset of line types or None for all) and the read-only `findNext(sp, line, col, opts)`, which returns a `Match(line, col, length)` or None. It doesn't wrap around (`startPos(sp, up)` is where a whole-script search starts), and going up a match must end at or before `col`. Each paragraph is searched as one string, its lines joined by `config.lb2str(lb)` (the offsets `rewrapPara` uses), so a match can run on from one line to the next: `length` counts characters in the paragraph's text, and `advance(sp, line, col, n)` gives the position n characters on (the end of a match, or with `length - 1` its last character, where the Find dialog puts the mark). The Editor side is `ed.replaceRange(line, col, length, text)`, the one replace primitive, which takes the same kind of length: one undo step, rewraps the paragraph, and leaves the cursor just past the new text (or at its start) wherever the rewrap put it. On top of it are `ed.replaceAt(match, text, up)` and `ed.replaceAll(opts, text)` (every match in the script, one undo step). Callers paginate. `finddlg.FindDlg` is only the UI: the last match, the "continue at the start?" question, and `FindState`, which is what the dialog was left showing (`MyCtrl.findState`). `spellcheckdlg` uses `replaceRange` and `spellcheck.suggest(word, dicts, n)`, the n closest words. Misspelled words are also underlined as you type (the global `checkSpelling` setting): `ScriptPainter` takes the user's dictionary and draws `SpellChecker.lineErrors(line, cursorCol)` for each visible line, skipping the word that ends at the cursor, and `MyCtrl.spellingMenu` puts the suggestions and the add-to-dictionary items at the top of the right-click menu (`spellcheck.wordAt`). The main dictionary is loaded at startup and when the setting is applied, and nothing is underlined without it. Tests: `tests/test_search.py`, `tests/test_spellcheck.py`, and `tests/test_finddlg.py`, which drives the dialog's handlers on a `FindDlg.__new__` with stand-in controls.
- Thesaurus: `thesaurus.py` (wx-free) loads `thesaurus_en.dat`, which `tools/make_thesaurus.py` makes from WordNet 3.0 (the format and the license are at the top of each). `Thesaurus.lookup(word)` returns its `Sense`s (headword, part of speech, definition, words cased like `word`), finding the headword through WordNet's irregular forms and regular endings (`headwords`: "walked" -> walk, "ran" -> run). The words come back in the clicked word's form (`headForms` says which ending it has, `inflect` puts it on each synonym: "looks" gives "stares", "angrier" gives "more furious"), using the X lines (forms with their part of speech and ending, the first one used) and `regularForm`'s spelling rules; proper nouns and most phrases stay as they are, and senses whose part of speech can't have the ending are left out (the noun "walk" for "walked"). A past tense ("ed") and a past participle ("en") are separate endings: `lookup(word, before)` takes the text before the word, and `auxiliaryBefore` finds a has / was / 'd... there, so "walked" gives "went" but "has walked" gives "gone". The generator makes the X lines from WordNet's exception lists, classing each irregular verb form as past tense, participle or both, putting US and regular spellings first ("traveled", "dreamed"), and using the spelling dictionary (`dict_en.dat`) plus WordNet's lexicographer files to add lines with the word itself as the form for plurals and comparatives that aren't used ("advice", "male", not "advices", "maler"), or "more X" where "-er" isn't one ("more boyish"). `MyCtrl.synonymsMenu` makes the right-click menu's Synonyms submenu from it (loading it the first time, `trelbyctrl.loadThesaurus`), passing the paragraph's text before the word, and picking one replaces the word with `ed.replaceRange`, keeping a possessive's "'s". Tests: `tests/test_thesaurus.py`.
- Beat board: `screenplay/beatboard.py` (wx-free) has `BeatBoard` (`sp.beatBoard`, saved in the file's `Beat-Board` section) of `Beat` cards: text (first line is the title, drawn in capitals with a line under it), x / y in unscaled pixels, a color (new cards get `DEFAULT_COLOR`, yellow; None is the theme's), a size once resized (`width` / `height`, None for the default size; `setSize` clamps to `MIN_CARD_WIDTH` / `MIN_CARD_HEIGHT` / `MAX_CARD_SIZE`), and maybe a picture (`image`: a PNG or JPEG file's bytes, base64 in the file, so the script doesn't depend on where it came from). It's kept apart from the scenes and the outline on purpose: cards don't link to scenes. `ed.setBeatBoard(board)` replaces the board as one undo step (`undo.BeatBoard`). The board is a view mode: View > Beat board, the toolbar's toggle at the right, Ctrl+Space (`beatboardview.BOARD_TOGGLE_KEY`, a fixed menu command; it was Set mark's, and `ConfigGlobal.load` takes it off Set mark in older configs) or the right-click menus' Go to beat board / Go to script items (`frame.setShowBeatBoard`, `gd.showBeatBoard`, not saved), makes every tab show `ui/beatboardview.BeatBoardView` in place of the script and the outline (`MyPanel.showBeatBoard`). The view works on a copy of the board and commits each change (add, move, edit, color, delete) with `ed.setBeatBoard`; `reload()` takes the script's board again after undo / redo (`scriptactions.reloadBoard`) and when `MyCtrl` gets a new script. While it's shown, `MyCtrl.SetFocus` gives the board the focus, and the Actions in `menus.SCRIPT_ONLY` (plus `ElemTo*`) are greyed out and do nothing, so the hidden script can't be edited, except those in `menus.ON_BOARD` (Paste), which run a board method instead (a greyed-out item's accelerator would swallow Ctrl+V). It has its own zoom level (`gd.boardZoom`, saved, stepping through `BOARD_ZOOM_LEVELS`): while it's shown, the zoom commands, the status bar and Ctrl+wheel act on it (`gd.currentZoom`, `frame.setBoardZoom`, `view.setZoom`, which keeps the point under the mouse in place), and the view scales board coordinates with `px` / `unpx` instead of `FromDIP`; the cards' text is Courier Prime (`cardFont`). Its background is a generated paper texture (`paperShading`, made once, seamless, the same every time; `paperTile(color)` tints it to the theme's workspace color, cached in `view.paper`), fixed to the board but not zoomed, with the grid drawn over it. Double-click to add or edit a card inline (`startEdit`), each card's × in its top right corner deletes it (`closeRect`, `closeHitTest`, `hover`), drag to move, right-click for color / delete. Several cards can be selected (`view.selection`, a list; `selected` is the last one): ctrl / shift-click toggles one (`toggleSelected`), dragging on the empty board draws a box that selects the cards it touches (`band`, `bandTo`; with ctrl / shift it adds to them), Ctrl+A (and Edit > Select all, through `menus.ON_BOARD`) selects all, Escape none. Dragging a selected card moves them all, kept on the board together, and Delete, the right-click menu's color, reset size and delete act on them all (`deleteCards`, `setColor(beats, color)`, `resetSizes`), each one undo step; a click on one of several selected cards without moving it selects it alone. Also middle-drag or space + drag to pan. Pictures come from the right-click menu (a file dialog), dropping files or pictures from other programs on the board (`BoardDropTarget`), or pasting (`paste`); `imageData` keeps a PNG / JPEG as it is if it's small enough (`beatboard.MAX_IMAGE_SIDE` / `MAX_IMAGE_BYTES`) and otherwise scales it down and re-encodes it (`encodePicture`: PNG with transparency, else JPEG). Dragging a card's bottom right corner (`gripRect`, `RESIZE_GRIP`; shift keeps its shape) resizes it as one undo step, and the right-click menu's Reset size goes back to the default. A picture card that hasn't been resized is sized to its picture (`cardSize`, fitted in `PICTURE_WIDTH` x `PICTURE_HEIGHT`); a resized one fits its picture in the card (`pictureArea`, scaled up or down, centered), with its title as a caption below; the view caches the decoded pictures and scaled bitmaps by the image bytes. Acts (`beatboard.Act`, `board.acts`, the board's own, not the script's act breaks): a titled frame (x / y / width, color, `folded`) holding cards in order (`act.beats`, the same `Beat` objects as `board.beats`, a card in one act at most; saved as `Act/N/Cards` of card numbers). `Act.layout(sizeOf)` puts its cards left to right in rows that wrap at its width and works out its `height` (not saved); the view calls `board.layout(view.cardSize)` in `layout()`, which `commit` and `reload` run, so card positions in acts always follow the order. `insertIndex(x, y, sizeOf, skip)` is where a drop lands; `remove` / `takeOut` / `shownBeats` (cards in folded acts are neither drawn nor hit). Acts are drawn under the cards (`drawAct`): the title bar has a fold arrow (`actFoldRect`), the title (double-click renames, `startTitleEdit`, shares `self.editing` with card edits) and an × (`actCloseRect`, deletes the act, keeping its cards); dragging the title moves it (`actDrag`), its bottom right corner sets its width (`actResize`). `actHitTest` / `actAt` (nothing on top) give the part under the mouse. Dragging cards sets `dropTarget` (act, index) from the mouse position, drawn as an accent line (`drawDropMark`); on drop they go in that act in reading order, or out of their acts. Double-click in an act's body adds a card there; picture cards dropped on one go in it (`putInActAt`). Right-click: Add act here, Put in new act (`addActAround`), Take out of act, the act's rename / color / collapse / delete (with or without its cards), collapse / expand all. Tests: `tests/test_beatboard.py`, `tests/test_beatboardview.py` (paints the board into a bitmap and drives it with made-up events, on a stand-in panel), `tests/test_beatboardacts.py`.
- Script formats: `screenplay/scriptformats.py` (wx-free) has `FORMATS` of `ScriptFormat`s (screenplay, sitcom, stageplay, audiodrama, comic; AV / two-column isn't one, as it would need a real two-column layout). A format adds no element types: `apply(cfg)` resets the element types and `FORMAT_VARS` (`pbActNewPage`, `pbSceneNewPage`, `sceneContinueds`) to the defaults, then lays them out its own way, keeping paper, margins, fonts and strings, and sets `cfg.scriptFormat` (saved as `ScriptFormat`; unknown keys are taken as a screenplay). The format's own names for element types (`labels`, e.g. Action is "Stage direction") and the ones it doesn't use (`hidden`) are shown through `typeLabel(cfg, lt)` / `usedTypes(cfg)` in the toolbar's element bar (`MainToolBar.setElemTypes`, from `frame.showScriptState`), the right-click menu (`makeRightClickMenu` takes the cfg), the status bar and the Elements settings page; the file still uses the usual names. `pbSceneNewPage` (Formatting page) starts every scene but the first on a new page, unless an act break or scene heading is right before it (`getScenePageStarts`, added to `sp.pageStarts` with the act starts). File > New screenplay (`NewScript`) / New from template (`NewScript-<key>` → `frame.OnNewScript(key)` → `ctrl.useFormat`) and Script > Change format (`scriptactions.changeFormat`, `dialogs/scriptformatdlg.py`, which clears undo like the settings dialog). MCP: `create_script` takes `format`, `get_script_info` returns it, and the server instructions say what each format's element types stand for. Tests: `tests/test_scriptformats.py`.
- Folding acts in the outline: `OutlinePanel.folded` is a set of act keys (`outline.actKeys`: an act break's heading and how many before it have the same one, so they survive edits; cleared when the tab gets another script). `makeRows` turns the items into the list's rows, `(first, last)` item ranges, a folded act being one row from its act break to the item before the next one, so the list's indexes are rows (`rowItem`, `rowLines`, `findItem`). The arrow left of an act's heading (`OutlineList.isFoldToggle`, `folds`: per row None or (folded, scene count)), Left / Right and the right-click menu fold and unfold (`toggleFold`, `setFolded`, `foldAll`); the cursor inside a folded act selects its row. Moving a row moves its whole range (`ed.moveSceneTo(line, newIndex, count)`), and `revealCursor` unfolds the act a moved or added scene ended up hidden in. Tests: `tests/test_outlinefold.py`.
- Adding scenes from the outline: the outline's header has a split button, "+" (`ed.addScene(line)`, an empty scene heading) and an arrow with a menu of beat sheets (`screenplay/beatsheets.py`, wx-free: `SHEETS` of `BeatSheet`s, each beat a scene heading named after it, with its name again as a note and colored by act, and its description as the scene's action). Both go through `ed.insertScenes(line, lines)`: one undo step, after the scene containing `line` (the selected one, else the cursor's) or before the first if it's above it, replacing a script with no text or notes, cursor on the first new line. Tests: `tests/test_beatsheets.py`.
- Notes: `screenplay/notes.py` has `Note` (an immutable text + `resolved`), kept in `Line.notes` (a tuple) on the first line of the paragraph they're about, so they move with its text: `rewrapPara` gathers a paragraph's notes onto its new first line (so joining keeps both's), `joinLines` and paste carry them along, `getSelectedAsCD` copies them and `moveNotesForward` keeps them when only part of a paragraph is deleted, and they go with the paragraph's last character. Like every Line attribute they're in `Line.copy` / `__ne__`, `undo.lines2storage` and `mcptools.linesRevision`. Saved as `#Note` / `#Note-Resolved` lines before the line. Edits are `ed.addNote(line, text)` / `setNote(line, index, note)` / `deleteNote` (one `SinglePara` undo step each, the cursor staying put; index is among `sp.getParaNotes(line)`), and `sp.getAllNotes()` lists them. They replace the old note element type: `NOTE` is only kept so that `absorbNoteElements` can turn note elements into notes on the element before them, which `fileformat.load` does for old files and `ImportResult` for every importer (the importers add a format's notes as note elements after what they're about). Never printed; Fountain exports them as `[[notes]]` (after the speech, for a note in one), FDX as ScriptNotes in their paragraph, HTML optionally. The GUI is `ui/notesview.NotesPanel` (`panel.notes`, a card per note with an × that deletes it; an edit in place ends, kept, when the focus leaves it, so `MyCtrl.OnLeftDown` takes the focus itself since it doesn't skip the event), on the side panel's Notes tab (see below), and Edit > Add note (Alt+N, `MyCtrl.newNote`), which writes the note on a blank card beside the page (`ctrl.newNoteLine`, the painter's `newNoteLine`), falling back to the sidebar where there's no room for cards. Only View > Notes (or the side panel's toggle) or a click on a note icon opens the notes (`gd.notesShown()`, `frame.showSideTab(gd.SIDE_NOTES)`). `ScriptPainter.drawNoteMarkers` shows each note 20 pixels right of the page as a card with its first `NOTE_LINES` lines (resolved ones faded, one line), stacked below the one before where they'd overlap, or a note icon for the paragraph where there's no room (side by side, narrow windows); the script's text itself is never highlighted. `ctrl.noteMarkers` has `(rect, line, index)` (index None for an icon): a click puts the cursor on its paragraph and selects the note in the sidebar if it's shown (`MyCtrl.showNote`), a double-click edits it in place (`MyCtrl.editNote`: `ui/noteeditor.NoteEditor`, a text field over the card that follows it on each paint, `ctrl.noteEditor`; an icon's note is edited in the sidebar), a right-click gives `MyCtrl.noteMenu` (edit, resolve, delete), a click on a card's checkbox (`painter.noteChecks` / `ctrl.noteChecks`, same tuples) marks it resolved or not (`MyCtrl.toggleNoteCheckAt`), and hovering shows the whole text. MCP elements have `notes` (`[{text, resolved}]`). Tests: `tests/test_notes.py`, `tests/test_notesview.py`.
- Breakdown (production tagging): `screenplay/breakdown.py` (wx-free). A `Tag` (immutable: `category` key, element `name`, and the paragraph `text` it was made from, "" for something the text doesn't mention) is kept in `Line.tags` on a paragraph's first line, carried exactly like notes (`rewrapPara`, `joinLines`, `splitLine`, `getSelectedAsCD` / `paste`, `moveTagsForward`, `Line.copy` / `__ne__`, `undo.lines2storage` tuple[12], `mcptools.linesRevision`), saved as `#Tag category|name|text` lines (`fileformat.escapeTagText` / `parseTag`; unknown categories are kept and counted as `misc`). `CATEGORIES` are fixed (`Category`: key, label function, color); elements are the same if `elementKey` (category, name case-insensitively) matches. `sp.getLineTagSpans(i)` finds each tag's text as whole words anywhere in its paragraph, which `ScriptPainter.drawTags` highlights (tint plus a bar in the category color) when the saved global `gd.showTags` is on (Production > Highlight breakdown tags). `getBreakdownScenes` (each scene, plus the part before the first heading or after an act break only if something is tagged there), `getBreakdown(castSpeakers)` (`SceneBreakdown`s: number, heading split by `splitHeading`, page, length in eighths from `getEighths`, elements by category, the speaking characters from `iterSpeeches` counted as cast unless `castSpeakers` is False) and `getElementList`. Editor: `addTag`, `removeTag`, `addSceneElement` (no text, on the scene's first line), `renameElement` (also moves category), `removeElement(cat, name, line=None)` (scene or whole script), `getSelectedTagText`. GUI: the right-click menu's Tag as submenu and Remove tag items (`MyCtrl.tagMenu` / `OnTagMenu`, the selection if it's in one paragraph, else the word clicked), the side panel's Breakdown tab (`ui/breakdownview.BreakdownPanel`, `panel.side.breakdown`, `gd.SIDE_BREAKDOWN`, View > Breakdown, Production > Breakdown: this scene or the whole script, + adds an element via `dialogs/breakdowndlg.askElement`), Reports > Breakdown report (`reports/breakdownreport.py`), File > Export > Breakdown (CSV) (`export/breakdowncsv.py`, in `formats.EXPORT_FORMATS` as `breakdown`). MCP: elements have `tags`, `get_breakdown`, `get_script_info`'s `breakdown_tags`. FDX carries them as Final Draft's tagger data (`TagData`: every one of FD's standard `TagCategory`s with its fixed Id, `breakdown.FDX_CATEGORIES`; a `TagDefinition` per element, its Id a uuid5 of `elementKey` so exports are stable; a `Tag` per stretch of text tagged with the same elements, listing them as `DefId`s, which the `Text` runs name by `TagNumber`): `export/fdx.py`'s `FdxTags` marks each tag's `findSpans` in its paragraph and a tag whose text isn't there (scene elements) over the whole paragraph, and `importers/fdx.py` (`parseTagData`, `addTags`) makes a tag per stretch of text per element, a whole scene heading giving one with no text, FD categories mapped by name (`breakdown.categoryFromFdx`, unknown ones `misc`). The schema comes from FD-saved files and other tools' readers, not checked in FD itself; whether FD writes several `DefId`s in a `Tag` (used for overlapping tags) is a guess. Not in the Fountain export. Tests: `tests/test_breakdown.py` (FDX: `testFdx*`, on an FD-style `tests/fixtures/import/tagged.fdx`), `tests/test_breakdownview.py`.
- Alternates (alternate dialogue, like Fade In's and Final Draft's): `screenplay/alternates.py` (wx-free). An element's other versions are `Take`s (immutable: `text`, its paragraphs joined by "\n", and `fmt`, a format string over the whole text or None) in `Line.alternates` on the element's first line; the shown take is the element's normal text, so pagination, exports, reports and spell check know nothing of them. They're carried like notes but per element (`rewrapPara`, `joinLines`, `splitLine`, `getSelectedAsCD` / `paste`, `moveAlternatesForward` (an element's, so only `LB_LAST` ends one), `Line.copy` / `__ne__`, `undo.lines2storage` tuple[13], `mcptools.linesRevision`), so mid-edit they can sit on a later line of the element: `sp.getAlternates(line)` gathers the element's, and every edit puts them back on its first line. Type changes keep them, splitting leaves them on the first part (unless split at the start), joining keeps both's. `sp.getShownTake(line)` is the element as a Take. Editor: `setTakes(line, shown, others)` is the one edit (an undo step, `ManyElems`): it replaces the element's text with `_putTake` (keeping the first line's flags, each paragraph's notes / tags / page locks on the same paragraph or the last) and rewraps it, moving the cursor to the element's start if it was in it; `addAlternate` (the shown text, or a given take; None if a duplicate), `setAlternate`, `deleteAlternate`, `switchAlternate(line, index)` (the takes are a ring, shown first, so switching rotates it and keeps the order), `cycleAlternate(line, step)`, `keepAlternate(line, index=None)` (drop the others). Saved as `#Alternate format|text` lines (`fileformat.formatTake` / `parseTake`; older versions ignore them with the unknown-information warning). GUI: Edit > Alternates (`AddAlternate`, `NextAlternate` Alt+Right, `PrevAlternate` Alt+Left, `ManageAlternates`; commands and Actions, in `SCRIPT_ONLY`), the right-click menu's Alternates submenu (`MyCtrl.alternatesMenu` / `OnAlternateMenu`: the shown take checked, up to `ALT_ITEMS` others to switch to, then Add / Manage), `ScriptPainter.drawAlternateMarkers` (a badge with the number of versions left of the element's first line, `painter.altMarkers` / `ctrl.altMarkers`; a click shows the next one), and `dialogs/alternatesdlg` (`AlternatesDlg` over a wx-free `TakeList`: edit, new, show, move, delete, first is shown). `MyCtrl`'s wrappers (`addAlternate`, `switchAlternate`, `cycleAlternate`, `setTakes`) repaginate. MCP elements have `alternates` (texts, no formatting). FDX: each paragraph's `<Alts Current="n"><AltId>` and the top-level `<AltCollection>` of `<Alt Id>` paragraphs, as in Final Draft 12 / 13's own sample files; Current is taken as the shown take's place among them all (export writes 0, import rotates so the ones after it come first), an inference from those files, not checked in FD. Other exports have only the shown text. Tests: `tests/test_alternates.py` (model, file, MCP, FDX on `tests/fixtures/import/alternates.fdx`), `tests/test_alternatesview.py`.
- Scene synopses: `Line.synopsis` on a scene heading's first line (`sp.getSynopsis(i)`, None elsewhere, like `getSceneColor`), a short text shown only in the outline, never printed. Like every Line attribute it's in `Line.copy` / `__ne__`, `undo.lines2storage` and `mcptools.linesRevision`; rewrapping, copy and paste keep it with the heading (`paste` moves it down with a heading pasted before, like its scene lock). Saved as a `#Synopsis` line (escaped like notes). `ed.setSynopsis(line, text)` is one `SinglePara` undo step (empty text removes it). The outline shows it under the heading (`SYNOPSIS_LINES`), or the dimmed start of the action (`OutlineItem.summary`) when there's none; it's edited in `dialogs/synopsisdlg` from the outline's right-click menu (`OutlinePanel.editSynopsis`) or Edit > Edit scene synopsis (`EditSynopsis`, enabled only while the outline is shown with a scene selected: `scriptactions.canEditSynopsis`, `gd.outlineShown`). Imports: Fountain `= ` lines right after a scene heading (others stay notes, per `sectionsAsNotes`), FDX `SceneProperties/Summary`, Fade In's `synopsis` on a scene heading (`importers.common.addSynopsis`); the Fountain and FDX exports write them the same way. MCP elements and `list_scenes` have `synopsis` (`replace_scene` keeps it when left out), and the scene report has a Synopses option. Tests: `tests/test_synopsis.py`.
- Table read (Tools > Read aloud): the script read aloud from the cursor in the system's own voices, the narrator and each character in their own. `speech.py` (wx-free) is the engine, behind `Backend`: `voices()` (`Voice`: id, name, language, gender; the system default first), `speak(text, voiceId, rate, onDone)` which returns at once and calls `onDone(completed, error)` once from any thread, `stop()`, `close()`. `ThreadedBackend` runs one utterance at a time on a worker thread (`_run` / `_interrupt`, with `job.cancelled` checked under `lock` so a stop can't slip in before the engine starts). `systemBackend()` picks `Pyttsx3Backend` on Windows (SAPI 5; pyttsx3 is the optional `speech` extra, imported lazily, bundled in the exe; it makes a new `pyttsx3.Engine` per utterance, since pyttsx3 2.99's SAPI driver cuts short every utterance after the first on a reused engine), plus the voices installed by Windows' Settings, which SAPI doesn't list: `extraVoices` reads them from `ONECORE_VOICES` (skipping the ones that are a desktop voice again) and `selectExtraVoice` gives the driver's `SpVoice` their token directly, since pyttsx3 can only select listed voices, `SayBackend` on macOS (the `say` command) and `EspeakBackend` on Linux (`espeak-ng` / `espeak`, with `+f2`-style variants for variety), or returns why there's none. Rates are words per minute; each backend has its `defaultRate`. `screenplay/tableread.py` (wx-free) is what's read: `utterances(sp, ReadOptions)` gives an `Utterance` (lines, text, speaker or None for the narrator, type) per element read, speakers from `speeches.iterSpeeches` (so they agree with the reports), no character names or parentheticals by default, `spokenText` spelling out INT. / EXT. and lower-casing headings and transitions; `indexAt(utts, line)` is where reading from a line starts, and `sampleText(utts, speaker)` the bit of a speaker's first line the Read aloud tab plays to hear their voice. `assignVoices(voices, characters(sp), genders, baseRate, overrides)` makes the `Cast` (`VoiceChoice`: voice id and rate): the narrator gets the default voice, characters (most speeches first) the least used voice / rate slot in their gender's voices, the narrator's slot shared last, then the voices again at `RATE_FACTORS`; deterministic, and `overrides` (by name, `NARRATOR` for the narrator) win, their slots counted as taken before the rest are given out. The voices chosen by hand are `VoiceSettings` (`sp.readAloud`, `choices`: name -> `VoiceChoice`, saved in the file's `Read-Aloud` section, a change marking the script changed without an undo step), and `usableChoices(voices)` drops ones whose voice isn't installed. Genders come from `guessGender(name, parseNameGenders(names.txt))`: words like MRS. / WAITRESS / FISHERMAN, else the name database's counts. `ui/tablereader.TableReader` (`frame.reader`) is the GUI (`makeCast(sp)` makes the cast from the voices, the script's choices and the guessed genders; `recast(ctrl)` remakes it mid-read; `preview(text, choice)` plays a sample; every change of state or element calls `frame.readerChanged`, which updates the Read aloud tabs): `toggle` (start at the cursor / pause / resume, pause stopping the element and resume re-reading it), `stop`, `skip(±1)`, each utterance's end passed back with `wx.CallAfter` and a token so a stopped one's end is ignored; it moves the cursor to the element and highlights it (`MyCtrl.readingLines`, drawn by `ScriptPainter.drawReadingLine`). It stops when the script changes (`MyCtrl.updateScreen` calls `checkScript`, comparing `changeMarker`: the sp, the Editor and the undo history's last / current), on a tab switch, the beat board, Escape, and closing. Commands: `ReadAloud` F5, `ReadAloudStop` Shift+F5, `ReadAloudNext` F6, `ReadAloudPrev` Shift+F6, `ToggleReadAloud` (View > Read aloud). The side panel's Read aloud tab (`ui/readaloudview.ReadAloudPanel`, `panel.side.readAloud`, labeled "Read") has play / pause, stop, previous / next, the cast as a grid (`CastList`, a drawn `wx.VListBox` under a `CastHeader`: a row per speaker, narrator first, with their voice and speed, sized to its rows so that what's below sits right under it), and below it the selected row's voice and speed drop-downs and a button to hear them (or double-click a row); changing one stores every shown speaker's voice in `sp.readAloud` (`OnChoice`), so that `assignVoices` doesn't move the others to make room, and the tools' reset button clears them. Tests: `tests/test_speech.py` (fake engines, and a real subprocess for `CommandBackend`), `tests/test_tableread.py`, `tests/test_tablereader.py` (the reader on a stand-in ctrl and backend), `tests/test_readaloudview.py`.
- Revisions: `screenplay/revisions.py` (wx-free). Marks are per character in `Line.revs` (like `fmt`: `chr(48 + level)` per character, `"0"` unrevised, None for none; level 1 = Blue, 2 = Pink... `levelName`, `COLORS`, up to `MAX_LEVEL` = Triple Cherry). Edits don't maintain them: every undo object's `setAfter` calls `undo.carryRevisions`, which runs `revisions.carry(before, after, level)`: a paragraph diff then a word diff, unchanged text keeping its old marks and changed text getting `sp.revisions.markingLevel()` (0 when revision mode is off, when changed text keeps whatever its line had, so moved scenes keep their marks); deletions mark the character before, type changes the whole paragraph. So any new undoable edit is marked for free, and anything that rewrites revs by hand passes `carry=False` (`FullCopy.setAfter`, as `clearRevisionMarks` does). `AnyDifference` widens its block by a line each side in revision mode so deleted paragraphs can mark a neighbor. Wrapping carries revs (`revisions.join`, `wrapLine`) for the rewraps that aren't undo steps. `sp.revisions` (`Revisions`: `level`, `active` = revision mode, `dates`, `markChar`, `showInHeader`, `currentOnly`) is saved in the file's `Revisions` section, the marks as `#Revised` lines; changing it marks the script changed without an undo step. `render` prints the mark at `revisions.markX` on marked lines (`Revisions.isMarked`) and the page's revision label (`${REVISION}` in `headers.pageVars`, from `sp.getPageRevision`) above the header unless a header has `${REVISION}`; `render.generatePML(sp, revisedOnly=True)` / `export.generatePDF(sp, True)` keep only `sp.getRevisedPages()` (pages with the current level). `ScriptPainter.drawRevised` / `drawRevisionMarks` show them on screen. GUI: the Production menu (`productionMenu` in `menus.makeTable`): revision mode (`ToggleRevisionMode`, a check item via `Action.isChecked`; `Revisions.toggleActive` starts Blue, dated today, if no revision has been started; turning it on runs `ed.lockForRevisions()` when `Revisions.autoLock` is set (the default, saved as `AutoLock`), which locks the pages and the scene numbers that have no locks at all as one undo step), `dialogs/revisionsdlg.py`, Show scene numbers (`ToggleSceneNumbers`, the `pdfShowSceneNumbers` script setting, toggled without `applyCfg` since it doesn't change wrapping, so undo survives), locking scenes and pages, Omit scene, Export revised pages, Clear revision marks; and the status bar's page field. Omitted scenes (`locks.py`): a scene heading reading `OMITTED` keeps its locked number; `ed.omitScene()` makes one, `AnyDifference.setAfter` calls `sp.omitDeletedScenes` so deleting a locked scene's heading leaves one (not for an OMITTED heading itself), and `paste` takes a cut scene's number back, removing its OMITTED heading (`removeOmittedScenes`). FDX: `export/fdx.py` splits Text runs by format and revision (`RevisionID` = level), writes a `<Revisions>` element (a `Revision` set per level up to the current / latest used, `ActiveSet`, `RevisionMode`) and scene headings' `Number` when scenes are locked or numbers printed; `importers/fdx.py` reads `RevisionID` back into revs (`addElem(..., revs)`) and `<Revisions>` into `ImportResult.revisions`, which `MyCtrl.importFile` applies (FD's own set names and colors aren't kept; `Number` isn't imported). Tests: `tests/test_revisions.py`.
- Headers and footer: `screenplay/headers.py` has `Headers` (`sp.headers`, strings at the top of every page but the first, which take lines from the page) and `Footer` (`sp.footer`: left / center / right text centered in the bottom margin, so pagination ignores it, plus `showOnFirstPage`; saved as `Footer-*` lines, only when it isn't empty). Both fill in `VARIABLES` (`${PAGE}`, `${PAGES}`, `${TITLE}`, `${AUTHOR}`, `${DRAFT}`, `${DRAFTDATE}`) with `expand(text, pageVars(sp, pageNr))`; the title page ones come from the title strings of each kind (`titleVars`, which guesses the kinds of old strings without setting them). `render.generatePMLPage` adds the footer before the script lines, since the page views take the last text on a page as the bottom of the script. The dialogs are `headersdlg` and `footerdlg`, whose `showVariablesMenu` is the "Insert variable" button of both. Tests: `tests/test_footer.py`.
- Word export: `export/docx.py` (`generateDocx`) writes the zip with the standard library, no python-docx: a paragraph style per element type (indents, widths and spacing from the config, half a character of slack so Word doesn't wrap a full-width line early), the title pages as frames in a section of their own, then the script's section with the headers (not on its first page, `titlePg`) and footer as header / footer parts, `${PAGE}` / `${PAGES}` as PAGE / SECTIONPAGES fields. Word paginates itself; only `sp.pageStarts` (acts, scenes on new pages) become `pageBreakBefore`, with the space before dropped as Trelby does at a page's top. Dual dialogue is a borderless two-column table (`getDualLines`). Notes, revision marks and scene numbers aren't exported. Tests: `tests/test_docx.py`; to check it in Word, open it through COM (`Word.Application`, `Documents.Open`, `SaveAs2(path, 17)` for a PDF).
- Export and import formats are listed once, in `formats.py` (`EXPORT_FORMATS` / `IMPORT_FORMATS`: key, file dialog name, menu label, extensions, the export function or the importer module, options, binary flag). The File menu, its file dialogs, `mcptools.export` and the MCP tool's `format` argument all use it, so a new format goes there. Its texts are functions (`lambda: _("...")`), since the lists are made before the translations are loaded.
- Importers: `trelby/importers/` has one module per format (`astx`, `celtx`, `fadein`, `fdx`, `fountain`, `pdf`, `text`), each with `parse(data, options=None)` returning an `ImportResult` (`lines`, and `titlePages` to replace the script's, or None). `data` is the file's contents, bytes if the module's `BINARY` is set (the zip formats and PDF), otherwise str. Errors raise `ImportFailed`, whose `message` is for the user. `common.py` has the shared helpers (`addElem`, `parseXML`, `checkNotEmpty`, `checkLines`). Fountain and text have an `Options` class: Fountain's carries the script's title pages, which it puts the titles on a copy of, finding Title / Author / Contact's strings by `TitleString.kind`; the text importer is split into `guessIndents` and `parse` with `Options(lineTypes=...)`, because the user fixes the guesses in `ImportDlg` in between. The PDF importer (`pdf.py`, for PDFs with text in them, not scanned ones) reads the text with its positions through pypdf, takes out the page furniture (page numbers and other repeated headers and footers, CONTINUED, (MORE) and the next page's (CONT'D) name, scene numbers), lines up right-aligned transitions and puts dual dialogue's columns one after the other, and turns the rest into formatted text indented in Courier characters from the page's left edge, which it imports with the text importer, `ImportDlg` step included (`text.Options.sceneLines` carries the lines it takes as scene headings without INT. or EXT., like "I/E." or a line in capitals on its own). Leading pages of mostly centered text become the title pages. pypdf is an optional extra (`pip install trelby[pdf]`), imported only when a PDF is read, and bundled in the exe; without it the import says so. Its fixture `sample.pdf` is made by `tests/pdffixture.py` (laid out like other programs' PDFs), and `testPdfRoundTrip` imports Trelby's own export of `sample.trelby`. `myimport.importFile(fileName, fmt, frame, sp)` is the GUI around them: it reads the file, asks for the options (`ASK_OPTIONS`, by format key), shows the errors, and returns the result, which `MyCtrl.importFile` applies to a new script. Tests: `tests/test_importers.py` pins each format's output on the samples in `tests/fixtures/import/`, through `myimport` with the dialogs answered (`tests/importrun.py`) and through `parse` directly.

## Model and GUI modules

The model imports without wxPython, so the MCP server and anything else working on `.trelby` files runs without it: `screenplay` (including `screenplay.search`), `config`, `commands`, `keys`, `formats`, `util`, `textutil`, `misc`, `pml`, `spellcheck`, `speech`, the reports, `mcptools`, `importers`... `tests/test_imports.py` checks this (`testModelDoesNotImportWx`), and that each listed module can be the first trelby import. Keep it that way: a model module must not import wx or a GUI module; pass it the data instead (e.g. `spellcheck.loadDict(s)` takes the dictionary's text, and the GUI's `spellcheckdlg.loadDict(frame)` reads the file, with message boxes on errors).

Where things live:

- `misc`: the platform, path and version globals (`init`, `isWindows`, `progPath`, `confPath`, `scriptDir`...), `getFullPath` and `mnemonic`.
- `textutil`: text helpers (case mapping, character classes, `wrapText`, escaping, words). `util`: the other wx-free helpers (numbers, `atomicWrite` and other file helpers, finding the PDF viewer, `ALIGN_*`, `getTextWidth`).
- `config`: `Config` / `ConfigGlobal`, no wx. `commands`: `Command`, the default command table (`defaultCommands()`, which must stay in alphabetical order), the key binding helpers (`addShiftKeys`, `removeKey`, `getConflictingKeys`), and what a key press in the editor does: `makeKeyMap` (via `cfgGl.getKeyMap()`, kept in `gd.keyMap`) and `resolveKey`, which returns the character to type or the `Command` to run. `keys`: `Key`, `MyKeyEvent`, and copies of the `wx.WXK_*` codes it uses (`tests/test_keys.py` checks them against wx).
- GUI: `gutil` (text extents and fonts, drawing, `finishWindow`, small helpers for wx controls like `createStockButton` and `getSpinValue`, and `messageBox` / `loadWxTranslations`), `fileio` (`loadFile` / `loadMaybeCompressedFile` / `writeToFile` and `showPDF` / `showTempPDF`, which show message boxes on errors), `icons` (`svgBitmap`, `getBitmap`), `theming` (giving dialogs and other windows the theme's colors: `themeWindow`, `themeAllWindows`, `setTitleBarColors`, plus `currentCfgGui`, `isDarkAppearance`, `blendColors`; it also pads push buttons and, on Windows, draws them and drop-down lists (`wx.Choice`, read-only `wx.ComboBox`) itself in `cfgGui.buttonBgColor` with a border halfway between the background and text colors (`BORDER_STRENGTH`), full text color when focused), and `widgets` (`Separator`, `WrappedText`, `ThemedListBox`, `ThemedListbook`, `ThemedTextCtrl` (a multiline text field with themed scrollbars: use its `.text`), and the bold / italic / alignment toggles). Then `configgui` (`ConfigGui`, the theme), `tabctrl`, `toolbar`, `mrufiles`, and the small dialogs `checkboxdlg`, `textdlg`, `keydlg`, `scriptchooserdlg`. `checkboxitem` is the wx-free item class `CheckBoxDlg` uses.
- Reports (wx-free): `textreport.TextReport` is the base of the scene, location, character and script reports. Each lays itself out once in `format(tf)`, rendered to PDF (`generate`) or HTML (`generateHtml`); its checkbox options are a class-level `options` list of `(name, label function)`, with the current values in `report.opts`. Who speaks where comes from `screenplay.speeches.iterSpeeches(sp)` (a `Speech` per speech: name, character line, start / end, dialogue and parenthetical lines, scene), and the reports, the dialogue chart and the MCP tools (`getInfo`, `listCharacters`) all count from it, so they agree: the module's comment has the rules (names normalized like the character profiles', only dialogue lines counted, dialogue with no character left out). `tests/test_speeches.py` checks that they agree. `scenereport.splitScenes` splits the script at scene headings and act breaks. `dialoguechart` has the chart's data (`DialogueChart`), its sort orders (`SORTS`), and its layout (`generateDoc`). Their windows are in `reports/reportframes.py`, on `reportwindow.ReportFrame` / `TextReportFrame`. `tests/test_reportoutput.py` compares every report's output with `tests/fixtures/reports/`; after an intended change, rewrite those with `.venv/Scripts/python -m tests.reportdump` and check the diff.
- `pml.BOLD` etc. are defined in `fontinfo` and re-exported by `pml`, since `util` imports `fontinfo` and `pml` imports `util`.

## The main window and the editor

The GUI around one script is split up like this:

- `trelbyframe.MyFrame` (`gd.mainFrame`): the main window. It holds the tabs (`tabctrl`), each a `trelbypanel.MyPanel` with the script's `MyCtrl`, its scroll bar and the side panel, and does the app-wide work: opening, importing and closing scripts, the view mode, zoom, fullscreen, the language, and applying the global settings (`applyGlobalCfg`, which updates every tab). `self.panel` is the current tab.
- `menus.py`: one table (`makeTable`) of `Action`s, one per menu item, toolbar button and menu keyboard command: name, id, label, mnemonic, accelerator, what it runs (`OnScript(scriptactions.f, *args)` or `OnFrame("method", *args)`) and `canUse(frame, ctrl)`, which greys it out. `build` makes the menu bar from it, `bind` binds the ids (EVT_MENU and EVT_UPDATE_UI), and `makeRightClickMenu` makes the editor's right-click menu. A menu keyboard command (`Command.isMenu`) runs the Action of the same name (`frame.runAction(name)`), so a new menu command needs a `Command` in `commands.py` and an Action with that name. `elemTypes()` is the list of element types the toolbar and the right-click menu show.
- `scriptactions.py`: the menu commands that work on one script, as functions `f(frame, ctrl, ...)`: the script dialogs, reports, export, find, goto, clipboard, undo... `frame` is the dialogs' parent.
- `trelbyctrl.MyCtrl`: the editor widget for one script: its file (load, save, autosave), mouse and keyboard input, scrolling, and keeping the screen up to date (`updateScreen`, `makeLineVisible`). `OnKeyChar` uses `commands.resolveKey`: a character is typed, a menu command goes to `frame.runAction`, and other commands run `EDITOR_COMMANDS[name]` on the Editor or a `cmd<name>` method (for the few that need the window, like page up / down).
- `scriptpainter.py`: drawing the script (`ScriptPainter.paint`). It gets a `Viewport` (the script, its Editor, the screen fonts, the window size and the scale) instead of the `MyCtrl`; the view modes (`viewmode.py`) accept one in place of a ctrl when laying out the screen.
- `toolbar.MainToolBar` (the toolbar's buttons and its element type / format / centering controls) and `statusbar.MainStatusBar` (the fields and the zoom buttons). Both run Actions by name for their controls, through `frame.runBarAction`. `frame.showScriptState(ctrl)` shows the current script's state in them.
- `sidepanel.SidePanel` (`panel.side`): the panel at the right of the script, with the outline (`outline.OutlinePanel`, `panel.outline`), the notes (`notesview.NotesPanel`, `panel.notes`) and the table read (`readaloudview.ReadAloudPanel`, `panel.side.readAloud`) as tabs. Its header has the tabs (`SideTabs`), the shown page's buttons (each page makes them in `page.tools`, a child of the header) and a close button. Whether it's shown, which tab and its width are global (`gd.showSidePanel`, not saved, so the app starts with it hidden / `sideTab` (`GlobalData.SIDE_OUTLINE` / `SIDE_NOTES` / `SIDE_READ_ALOUD`) / `sideWidth`), set through the frame for every tab: `frame.setShowSidePanel(show)`, `frame.showSideTab(tab)` (which also shows it), and `MyPanel.showSide` / `showSideTab` for one. One toolbar button and View > Side panel toggle it; View > Outline / Notes / Read aloud show that tab, or hide the panel if it's already showing it (`OnToggleSideTab`). Tests: `tests/test_sidepanel.py`.
- Typewriter scrolling and focus mode: View > Typewriter scrolling (`ToggleTypewriter`, the saved global `typewriterScrolling`, also on the Misc settings page) keeps the cursor's line at `viewmode.TYPEWRITER_POSITION` of the window's height: `MyCtrl.makeLineVisible` calls `vm.scrollLineTo(ctrl, line, y)` instead (`ctrl.isTypewriter()`; not in side by side, `ViewMode.typewriter`), which picks a top line and sets `ed.topOffset`, the pixels the draft and page views draw the screen down (or up) by, so the line lands exactly there, at the start of the script too (blank space above it). `MyCtrl.scrollBy` (the wheel) scrolls that offset away first; the scroll bar and turning it off reset it (`frame.scrollingChanged`). Clicks don't scroll; Page Up / Down move the cursor by a screenful. View > Focus mode (`FocusMode`, Shift+F11, fixed; `gd.focusMode`, not saved; `frame.setFocusMode`) only fades everything but the cursor's element or scene into the page (the global `focusDim`, `config.FOCUS_DIM_*`, through `ctrl.focusLines()` and `ScriptPainter`'s `focusLines` / `FOCUS_FADE`), skipping the faded text's spelling underlines. - `recoverydlg.py`: offering to restore autosaved recovery copies at startup.
- Writing log: `writinglog.py` (wx-free) is every writing session in every script, one global file (`gd.writingLogFilename`, `writinglog.json` in the config directory, loaded at startup by `gd.loadWritingLog`, an unreadable one kept as `.bad`; `gd.saveWritingLog` writes it atomically when `log.dirty`, without message boxes). A `Session` has start / end, the script's absolute path (None if never saved) and name (`writinglog.scriptName`, or the untitled name), the net words and pages it added (`sp.getWordCount()` / `sp.getPageLength()`, so they can be negative) and its active seconds; it belongs to the local day it started on. `WritingLog.put` adds or replaces one by id (sessions are stored while still going on), and `dayTotal` / `days` / `streak` work out what Home and the status bar show (`Total.shownWords` never below 0). `writingsession.Tracker` (`ctrl.writing`) records them: `MyCtrl.updateScreen` calls `update(sp, ctrl.writingInfo)`, which does nothing unless `sp.changeCount` (bumped by every `markChanged(True)`) moved; a new `sp` in the tab is `watch`ed, ending the session and taking its counts as the base, so opening, importing or reverting isn't writing. Gaps over `IDLE` (3 min) don't add active time, and over `SESSION_GAP` (30 min) start a new session; the frame's `writingTimer` (every `WRITING_TIMER_SECONDS`) calls `tick` on every tracker and saves the log, and closing a script or the app ends its session and saves. Edits made over MCP in the app aren't the writer's: `AppDoc.changed` calls `ctrl.writing.exclude(sp)`, which moves the base by them. The daily goal is global (`cfgGl.dailyGoal`, 0 for none, and `dailyGoalPages`, saved as `Goals/Daily` / `Goals/DailyInPages`), shown in the status bar's `SB_GOAL` field (`statusbar.formatToday`, `MainStatusBar.showToday`). The goals are set on the Settings dialog's Writing Goals page (`dialogs/configpages/goalspanel.GoalsPanel`, opened there by Tools > Writing sprint > Writing goals or Home's row, `frame.OnWritingGoals` → `OnSettings(page)` → `CfgDlg.showPage`): `dailyGoal` / `dailyGoalPages`, `weeklyGoal` (same unit, the week from Monday, `WritingLog.weekTotal`, which adds the days' shown amounts), and the sprints' `sprintMinutes`, `sprintWords` (a word target that ends one early, 0 for none) and `sprintSound`. Writing sprints: `sprint.Sprint` (wx-free) counts the words as how much `WritingLog.totalWords` (the sum of all sessions' words, kept up to date by `put` through `log.counted`) went up since it started, so they're the same words as everything else, from any script; pausing stops its clock (`pausedFor`) but not the counting. `ui/sprinttimer.SprintTimer` (`frame.sprint`) runs one on a one-second `wx.Timer`: `toggle` (Action / command `ToggleSprint`, F7, a click on the status bar's goal field, Home's row) starts one with the settings or stops it, `togglePause` (`PauseSprint`, Shift+F7), and `finish` puts a `writinglog.SprintRecord` in the log (`log.sprints`, saved as the file's `sprints`), saves it, chimes if it ran its course (`chime`) and shows `summaryText` (`showSummary`, which tests replace); `close` stops one silently as the app closes. Every change calls `frame.sprintChanged`, which updates the status bar (`showToday` shows `timer.statusText()`, the countdown, in place of today's writing) and refreshes Home, whose writing section has a Sprint part (the countdown, today's sprints, Start / Stop / Pause / Resume and Writing goals rows, with the command's key from `commandKeyText`). `ToggleSprint`, `PauseSprint` and `WritingGoals` work on Home (`menus.ON_HOME`). ## Code conventions worth knowing

- Data files are found relative to the package: `misc.getFullPath("trelby/resources/...")` (uses `misc.progPath`, the parent of the `trelby/` package) or `trelby.__path__[0]`. Use these instead of hard-coded or CWD-relative paths, or the exe build breaks.
- `misc.init()` sets `progPath = "."` in `--test` mode and in tests, so tests must run from the repo root.
- UI strings are wrapped in `_()` for gettext; translations live in `trelby/locales` and `po/` (see `TRANSLATION_NOTES.txt`).
- Version string is duplicated in `pyproject.toml`, `trelby/misc.py`, `doc/version.xml`, and `choco/`; bump all of them together.
- Packaging metadata and dependency bounds live in `pyproject.toml`; `requirements.txt` is the dev install (same bounds plus pytest). Keep them in sync.
- Menu/control IDs: use `wx.NewIdRef()` (not the deprecated `wx.NewId()`). `WindowIDRef` works as a dict key and in `Bind`/`Append`, but doesn't support arithmetic; convert with `int()` when you need it (see `mrufiles.MRUFiles`). Submenus use `AppendSubMenu`.
- Spacing: `gutil.finishWindow` widens every border, grid gap and fixed spacer in the layout by `gutil.SPACING` (1.5) and puts `MIN_GAP` between stacked items of vertical sizers that have none (`spaceSizer`), so write borders at the old, denser sizes (5 / 10 / 20). Layouts that don't go through `finishWindow` call `gutil.spaceSizer` themselves before `SetSizer` (the character profile form, the report windows).
- Right-to-left languages (Hebrew): `gutil.setLanguageDirection` (called at startup, from wx's language table) sets `gutil.layoutDirection`, and the main frame takes it before creating anything, so its children and the dialogs it parents inherit it; `finishWindow` applies it to parentless dialogs (`applyLayoutDirection`). The script and pages stay left to right: `gutil.keepLeftToRight(win)` (the editor panel, `MyCtrl`, beat board, outline list, title / header / footer previews, report `PageView`, splash, and the fields holding page or script text). In a mirrored window, a `wx.PaintDC` mirrors everything, except drawing on the dc while a `GraphicsContext` on it exists (draw dc text after `del gc`, as `tabctrl` does), and raw `BitBlt` of a bitmap mirrors its contents (use `NOMIRRORBITMAP`, see `theming._paintListHeader`). Every GDI+ `gc.DrawText` takes the direction of the first one in the process, so `setLanguageDirection` draws one left to right first, and theming draws labels in mirrored windows on the dc. Tests: `tests/test_layoutdirection.py`.
- Courier Prime (SIL OFL, `trelby/resources/fonts/`, `fontinfo.BUNDLED_FONTS` / `BUNDLED_FACE` / `bundledFontPath`) is the Courier font on screen and in PDFs, so both look the same. Screen: `gutil.init` loads it with `wx.Font.AddPrivateFont` (`loadBundledFonts`; on Windows GDI+ graphics contexts only see fonts added before the first one is created; on macOS, where `AddPrivateFont` only takes fonts in an app bundle's `Resources/Fonts`, through CoreText instead, `registerMacFont`). Font strings in the config go through `gutil.fontInfo`, since the default ones are Pango descriptions that only wxGTK's `FromString` reads and it's the default in `setDefaultFonts`, with `ConfigGui` falling back to `config.oldDefaultFace()` (Courier New / Monospace) if it didn't load. Old configs without `FontVersion` get Courier New (and the old Unix Monospace defaults) replaced once (`config.migrateFont`). PDF: `PDFExporter.getFontForFlags` embeds it for Courier text unless the script sets its own fonts on the PDF/Fonts page; `hasChar` checks a TrueType font's own characters, which `unsupportedChars` and the double-width CJK fallback use. It has WinAnsi, Latin Extended-A and a few Greek letters, but no Cyrillic. The title / header / footer previews (`titlespreview.faceName`) and the report windows draw Courier in `gutil.courierFace()`, the title dialog calls it "Courier Prime" (the file format still says `Courier`), and the HTML export asks for it first.
- High DPI: on Windows Trelby is per-monitor DPI aware (`trelby.enableDpiAwareness`, called in `main` before the app is made), so it draws in real pixels at each screen's scaling instead of being stretched (macOS and GTK scale by themselves). Write sizes in device independent pixels and convert them with `FromDIP` (`vp.dip` / `ctrl.dip` in the painter and view modes; a sub-pixel scale is `FromDIP(1000) / 1000`, not `GetDPIScaleFactor`, which is 2 on Retina). A memory DC on a plain bitmap measures and draws at 96 DPI, so give the bitmap `SetScaleFactor` (`MyCtrl.screenBuf`, `gutil.permDc`); `gutil.getTextExtent` / `getFontHeight` measure at `gutil.measureScale`, which the frame sets from its DPI at startup and on `EVT_DPI_CHANGED` (`frame.checkDpi`, which rebuilds `gd.cfgGui`). Draft view's `fontYdelta` setting and the saved window and side panel sizes are at 96 DPI. Windows font strings starting `0;` hold a pixel height at 96 DPI, which `gutil.fontInfo` turns into points. Don't call the toolbar's `SetToolBitmapSize`: it sizes tools from the icons' bitmap bundles. `tools/screenshot.py` takes the README's screenshot (`media/screenshot.png`).
- Font constants: use `wx.FONTFAMILY_*` / `wx.FONTSTYLE_*` / `wx.FONTWEIGHT_*`, not the old `wx.NORMAL` / `wx.BOLD` / `wx.MODERN`.
- To catch new deprecations, run the app with `.venv/Scripts/python -X dev -W always trelby.py --test`; startup should print no warnings.
